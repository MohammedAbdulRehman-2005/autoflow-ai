# AutoFlow AI X — List of Unresolved Backend Dependencies

This document records the backend capabilities and API contracts that are missing or incomplete in the current backend (`main.py`, `WorkflowRunner`, `database/models.py`), identified during the Stage 1 Production Readiness Audit and Stage 2 parallel workstream.

Until these dependencies are addressed on the backend, the frontend operates seamlessly via `apiBridge.js` and `mockService.js`.

---

## 1. Durable Execution & Replay Engine

| Missing Capability | Frontend Impact | Backend Root Cause | Stage / Priority |
|---|---|---|---|
| **Durable Execution & Restart Safety** | Runs cannot survive an API restart; runs become orphaned in `pending`/`running`. | In-memory `BackgroundTasks` instead of Temporal or durable orchestrator. | Phase 3 / P0 |
| **Replay from Step (`POST .../replay`)** | "Replay Run" button falls back to simulated re-run. | `WorkflowRunner` only supports running from beginning to end without step checkpoint resumption. | Phase 3 / P1 |
| **Execution Cancellation (`POST .../cancel`)** | In-flight execution cannot be halted from the UI. | Single synchronous loop in `WorkflowRunner` with no cancellation token listener. | Phase 3 / P1 |
| **Idempotency Key Persistence** | Idempotency key rendered in UI is client-generated. | `workflow_runs` table has no `idempotency_key` column or unique index constraint. | Phase 2 / P1 |

---

## 2. Recovery Center & AI Failure Diagnosis Subsystem

| Missing Capability | Frontend Impact | Backend Root Cause | Stage / Priority |
|---|---|---|---|
| **Incident Clustering (`/api/v1/recovery/incidents`)** | Triage queue currently populated by `mockService.js`. | No backend failure classifier service or incident persistence table. | Phase 4 / P1 |
| **Automated Patch Generation** | Side-by-side patch diff generated by AI is simulated. | LangGraph failure diagnosis agent is not connected to the API runner. | Phase 4 / P2 |
| **Sandboxed Dry-Run (`POST .../dry-run`)** | "Dry-Run Simulation" simulated in 600ms timer. | No isolated mock sandbox environment to execute speculative patches without committing external side effects. | Phase 4 / P2 |
| **Zero-Downtime Patch Application (`POST .../apply`)** | Patch applies to local mock state and updates run status. | No backend endpoint to mutate an in-flight workflow's payload state and signal the runner to resume. | Phase 4 / P1 |

---

## 3. Human Approval Queue & Governance Subsystem

| Missing Capability | Frontend Impact | Backend Root Cause | Stage / Priority |
|---|---|---|---|
| **Approval Signal / Pause Step** | "Awaiting Approval" state cannot be triggered by real workflow runner. | `WorkflowRunner` has no `PauseForHumanSignal` primitive or webhook callback listener. | Phase 4 / P1 |
| **Approval Inbox Endpoint (`/api/v1/governance/approvals`)** | Approval items rendered from `mockService.js`. | No database schema for approvals (`approval_requests` table) or role-based query filters. | Phase 4 / P2 |
| **Deterministic Policy Engine** | Policy badges (`COMPLIANT_AUTO_APPROVABLE` vs `REQUIRES_HUMAN_SIGN_OFF`) simulated. | No server-side policy evaluator (e.g. Open Policy Agent / Cedar / custom Python rules engine). | Phase 4 / P2 |

---

## 4. Workflows & Run Model Hardening

| Missing Capability | Frontend Impact | Backend Root Cause | Stage / Priority |
|---|---|---|---|
| **Immutable Workflow Versions (`workflow_versions`)** | UI displays version string (`v2.1.0`), but backend overwrites single JSON column. | `workflows` table lacks versioning; mutations overwrite `ai_context_json` without creating immutable snapshots. | Phase 2 / P1 |
| **Write-path DSL Validation** | Direct CRUD edits through `PATCH /workflows` bypass validator. | `crud/router.py` accepts unvalidated `dict` rather than validating against Pydantic `WorkflowDSL`. | Phase 1 / P0 |
| **Per-Node Secret Scoping** | Step Inspector output displays raw credentials if not scrubbed. | `CredentialManager` does not enforce per-node `credential_id` scoping across all executors. | Phase 1 / P0 |

---

## Summary for Backend Team

The Stage 2 frontend is completely unblocked. It introduces zero breaking changes to existing endpoints (`/api/v1/workflows`, `/api/v1/workflows/:id/run`, `/api/v1/ai/plan-workflow`, `/api/v1/workflows/node-types`), and all new advanced screens (Execution Monitor, Recovery Center, Approval Center) interact through the clean abstraction layer in `frontend/src/services/apiBridge.js`.
